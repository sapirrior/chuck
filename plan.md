# plan.md — Infrastructure Plan for `xd`

> **Scope of this plan:** This document tells an AI coding agent how to build the
> *scaffolding, governance, and documentation* of the `xd` repository — **not**
> the application logic of `xd` itself. No code inside `src/` should be written
> as a result of this plan. The output of executing this plan is a set of root
> documentation files, a validated directory skeleton, and tooling config —
> nothing more.

`xd` is a general-purpose AI terminal agent, written in **TypeScript**, using
the **Vercel AI SDK** for all model/tool-calling integration and **Ink** for
all TUI rendering. This plan exists so that once the real `src/` code starts
landing, adding a feature, fixing a bug, or reviewing a PR is "dead simple" —
because the rules, structure, and expectations were nailed down before a
single line of application code existed.

---

## 0. Guiding Principles (read this before generating anything)

1. **Infra first, logic never.** This plan produces docs, configs, and empty
   directories with `.gitkeep`/placeholder files. It never produces working
   agent logic, Ink components, or AI SDK integration code.
2. **Signal density over completeness.** Per current best practice on
   AGENTS.md-style files (industry research from 2026 shows LLM-generated
   context files that over-specify actually *reduce* agent task success and
   inflate cost), every root doc must be short, precise, and only contain
   instructions that cannot be enforced by tooling. If ESLint/Prettier/tsc can
   enforce a rule, the rule belongs in config, not in prose.
3. **One file per audience.**
   - `README.md` → humans, first impression. (Stub only — see §3.)
   - `AGENTS.md` → any AI agent (Claude, Codex, Cursor, Copilot, etc.) working
     in this repo. Universal behavioral rules.
   - `CONTRIBUTING.md` → humans *and* agents making actual code contributions.
     Process, standards, workflow.
   - `IMPORTANT.md` → a living manifest of temporary/manual/human-provided
     assets that are not code and not generated by the agent (see §4).
4. **Nothing in this plan invents application features.** Where the plan
   says "describe the module boundaries," it means describe *where future
   code will go and why*, not what that code does.

## 2. Directory Skeleton

Create the following top-level layout. Directories marked **(human-managed)**
should be created empty (with a `.gitkeep` or a one-line `README.md` stub
inside) — the agent must **not** populate their real contents. Directories
marked **(agent-managed)** are fair game for future feature work, but no
feature code is written *during this infra pass*.

```
xd/
├── src/                     (agent-managed) — application code goes here later.
│   └── .gitkeep             — placeholder only; do not add modules yet.
├── skills/                  (human-managed) — populated by the human with
│   │                          the ai-sdk and ink reference skills.
│   └── README.md            — one line: "Populated manually. See IMPORTANT.md."
├── references/              (human-managed) — populated by the human with
│   │                          delta_wit.xml (UI/theme/color reference only).
│   └── README.md            — one line: "Populated manually. See IMPORTANT.md."
├── AGENTS.md
├── CONTRIBUTING.md
├── README.md
├── IMPORTANT.md
├── package.json
├── tsconfig.json
├── .eslintrc / eslint.config.* (per current ESLint flat-config norms)
├── .prettierrc
├── .editorconfig
├── .gitignore
├── .nvmrc
└── LICENSE (if the human has chosen a license — otherwise omit and note it as pending in IMPORTANT.md)
```

**Do not create** `src/agents/`, `src/ui/`, `src/tools/`, or any other
feature subdirectory during this pass. `AGENTS.md`/`CONTRIBUTING.md` should
describe the *intended* boundary of such subdirectories in prose (so future
contributors know where things will go) without physically creating them —
this avoids the agent inventing an architecture prematurely.

## 4. `IMPORTANT.md` — Manifest of Manual/Temporary Assets

This file exists so that any human *or* any AI agent opening the repo cold
immediately understands which parts of the tree are **not** theirs to
generate or modify, and why.

Required content (the executing agent should write this out in full prose,
not just copy this outline):

- **Purpose statement:** this file tracks directories/files that are
  supplied manually by the project owner and must never be auto-generated,
  overwritten, or "completed" by an AI agent.
- **`skills/` directory:**
  - Will contain two skills, supplied by the human: one for the **Vercel AI
    SDK** and one for **Ink**.
  - These are reference/behavioral skills for whichever AI coding agent works
    on `xd` — they teach the agent correct, current API usage for both
    libraries. They are not application code.
  - The executing agent must never write, delete, or "improve" files inside
    `skills/` — it may only *read* them once they exist.
- **`references/` directory:**
  - Will contain `references/delta.wit.xml` (note the human's exact naming:
    the source upload is `delta_wit.xml`; document under `IMPORTANT.md` that
    it is expected at `references/delta.wit.xml` in the repo, and flag the
    naming — underscore vs. dot — as something the human should confirm on
    placement).
  - This XML is a **styling/theming reference only**: TUI color codes, theme
    tokens, palette structure. It must be treated purely as design reference
    data for Ink UI styling decisions.
  - **Hard rule, must be stated verbatim-equivalent in this file:** no logic,
    behavior, control flow, or architectural decisions may ever be derived
    from `delta.wit.xml`. It informs *how things look*, never *how things
    work*.
- **License status:** note whether a `LICENSE` file is pending human decision.
- **Anything else temporary:** a running list — as the human adds manual
  assets later (e.g. API keys/config templates, design mockups), they get a
  bullet here, not folded into `AGENTS.md`.

## 5. `AGENTS.md` — Universal AI Behavior Rules

Target length: roughly 30–60 lines. This is the file every AI coding agent
(Claude, Codex, Cursor, Copilot, etc.) reads first. Keep it terse; anything
enforceable by a linter/type-checker/CI job must live there instead of here.

Required sections (executing agent should write full prose under each, not
just headers):

1. **Project summary** (2–3 sentences): `xd` is a general-purpose AI terminal
   agent. TypeScript. Vercel AI SDK for all model/tool-calling. Ink for all
   TUI rendering. No other UI or AI-integration library is to be introduced
   without explicit human approval.
2. **Source of truth for library usage:** Before writing any AI-SDK or Ink
   code, the agent must consult `skills/` (once populated) rather than
   relying on possibly-stale training knowledge of either library's API.
3. **Styling source of truth:** Any TUI color/theme decision must be checked
   against `references/delta.wit.xml` (styling/theming only — reiterate the
   logic/styling separation from §4, briefly, with a pointer to `IMPORTANT.md`
   for the full explanation — do not duplicate the whole explanation here).
4. **Directory boundaries:** Describe (in prose, without creating the
   folders) the intended split inside `src/` once feature work begins — e.g.
   a boundary between agent/orchestration logic, tool definitions, and Ink UI
   components — so contributions land in a predictable place. Frame this as
   *guidance for future structure*, not a mandate to create it now.
5. **Build/test/lint commands:** Reference the actual `package.json` scripts
   once §7 defines them (e.g. `npm run build`, `npm run lint`,
   `npm run typecheck`, `npm test`) — do not restate what a script does, just
   name it.
6. **Never do:**
   - Never invent Vercel AI SDK or Ink APIs; if uncertain, check the skill or
     ask the human rather than guessing.
   - Never touch `skills/` or `references/` contents.
   - Never write feature code into `src/` as a side effect of a docs/infra
     task.
   - Never commit secrets, API keys, or `.env` files.
7. **Commit/PR expectations:** one line pointing to `CONTRIBUTING.md` for the
   full standard, so this isn't duplicated.
8. **When in doubt:** ask rather than assume; a wrong assumption compounds
   across a terminal-agent codebase faster than a stalled task does.

## 6. `CONTRIBUTING.md` — Contribution & Code Standards

This is the longer, human-and-agent-facing process document. Required
sections:

1. **Getting started:** Node version (pin via `.nvmrc`), package manager
   choice (state one clearly — npm/pnpm — and require it be used
   consistently), install/build/dev commands once defined in `package.json`.
2. **Project structure overview:** A slightly more detailed version of the
   `src/` boundary description from `AGENTS.md` §5.4, since contributors
   need this context too. Still prose-only, still no folders created yet.
3. **Code style:**
   - TypeScript strict mode is mandatory (`tsconfig.json` enforces this in
     §7 — reference it, don't re-specify the rules here).
   - Prettier for formatting, ESLint for linting — both enforced via config
     and a pre-commit/CI check, not via prose rules.
   - Naming conventions: files kebab-case, types/interfaces PascalCase,
     functions/variables camelCase — state briefly, since this is not
     linter-enforceable by default.
   - Ink components: one component per file, colocated with related hooks —
     state this as a guiding convention for when UI code begins, not an
     instruction to create it now.
4. **Commit message convention:** Adopt **Conventional Commits**
   (`type(scope): subject`, types: `feat`, `fix`, `docs`, `style`, `refactor`,
   `test`, `chore`; example lines included) since it is the dominant
   industry norm and unlocks automated changelog generation later.
5. **Branching model:** short-lived feature branches off `main`, no direct
   pushes to `main` once collaborators exist, PRs required for anything
   beyond trivial docs fixes.
6. **Pull request expectations:** what a PR description should contain
   (what/why, testing performed, linked issue if any); require passing
   lint/typecheck/test before merge.
7. **Testing expectations:** state the intended framework choice only if the
   human has specified one; otherwise mark as "TBD — to be decided before
   first feature PR" rather than guessing. Require new features to include
   tests once a framework is chosen.
8. **Working with `skills/` and `references/`:** short pointer to
   `IMPORTANT.md` — contributors read that file for the full rules; don't
   duplicate here.
9. **Reporting issues:** where/how (GitHub issues, template if one is added
   in §8).

## 7. Tooling Config (infra, not code)

Generate config files that make the rules above enforceable by tooling
rather than prose. No runtime/application logic:

- `package.json`: name `xd`, private (unless human says otherwise), scripts
  for `build`, `dev`, `lint`, `format`, `typecheck`, `test` (test script can
  be a placeholder `echo "no tests yet"` until §6.7 is resolved), dependencies
  section listing `ai` (Vercel AI SDK) and `ink` as intended core deps —
  **do not `npm install` or pin exact versions without the human confirming
  current major versions**; leave a `TODO` comment or note in `IMPORTANT.md`
  if versions can't be confirmed.
- `tsconfig.json`: strict mode on, modern target/module settings appropriate
  for a Node CLI + Ink/React JSX, path aliases only if genuinely needed.
- ESLint flat config + Prettier config: standard TypeScript rule sets: no
  invented custom rules.
- `.editorconfig`, `.gitignore` (Node/TS/Ink-appropriate — include
  `node_modules`, build output dir, `.env*`), `.nvmrc`.
